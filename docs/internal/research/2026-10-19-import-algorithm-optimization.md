# 导入算法优化考察

日期：2026-10-19。调查工单：`Serpent-wuu07`。依据：当前源码与隔离本地实验。

源码基线：`589d41aaa334c9b04c4623741ea7cdf45c4dafb3`。PR #70 候选为 `1fa2a49c79509aa95196b9fb78d6f0d105daae16`，尚未合入；用它剖析时仅为隔离目的地重复枚举后的剩余开销，不代表其正确性已通过。

## 当前执行过程

1. Main 根据入口及序列帧选择决定是否探测源目录中的序列。
2. Worker 枚举源文件，建立导入操作记录及初始目的地状态。
3. 把源文件复制到同库 stage：校验源文件快照，分块读写，刷新文件，再校验源与 stage 的状态。
4. 再读取 stage，一遍同时计算 SHA-256 和 SHA-1。SHA-256 保存在本次任务条目中，SHA-1 作为 revision 的 `content_fingerprint` 持久化。
5. 准备冲突摘要：名称冲突、内容重复与序列帧例外；必要时等待用户选择。
6. 应用阶段重新分类并确定最终名称，写恢复清单，备份替换目标，再将 stage 内部重命名到 Assets。
7. 普通导入逐资产提交数据库；事务内还包括图片尺寸探测及元数据、搜索内容更新；提交后逐项通知。
8. 收尾操作、生成结果摘要，再由 handler 恢复和安排媒体任务。

入口见 `src/worker/handlers/asset-ingestion.ts:101`。本地 service 基准不能替代 Main/Worker IPC、真实 UI、序列预探测和缩略图完成时间的测量。

## 从算法直接发现的问题

### 名称字段已有，但部分查询没有使用正确的约束

`assets.path_identity` 已有托管资产专用唯一索引（`library-service.ts:1353`），不需要先重复增加文件名字段。`resolveImport` 中 `library-service.ts:44942` 的查询却只有 `WHERE path_identity = ?`，缺少索引限定的 `location_kind = 'managed'`；这也没有正确隔离链接根的命名空间。合并重复资产的相关查询有同样问题（`:44896`）。

`findActiveManagedAssetAtPath`（`:42874`）使用 `LOWER(relative_file_path) = LOWER(?)`，既与项目的完整 portable identity 规则不同，也不等同于直接按已索引的规范化键查询。

优先统一托管资产查询的范围及名称比较方式，复用已存在的 `prepareCached`（`:10076`）。较大的批次可复用已有分块查询能力，仅预取本次需要的名称，不必像 PR #70 一样每次物化整个库的目的地 Map。

数据库查询不能替代对磁盘未登记文件的检查。更稳妥的配套方案是对本次访问的目的目录惰性建立实际名称到 portable identity 的映射，在短阶段内复用；stage 完成和用户确认后进入应用时重新验证受影响目录。名称歧义、符号链接、目录冲突和外部写入仍需保留原有处理。

### 内容查重反复执行关系查询

`findActiveManagedAssetByContent`（`:42788`）先按大小和已存指纹查找，无命中后再查同大小、缺指纹的资产。准备阶段和应用阶段都会调用这条链路。现有源码中 revision 指纹字段的添加没有附带大小/指纹索引。

应先用查询计划确认扫描位置，再选择匹配当前版本关系的索引与连接方式。候选为按 `(byte_size, content_fingerprint)` 缩小 revisions，通过 `r.asset_id` 连接资产主键，并同时核对 `a.current_revision_id = r.revision_id`，保留 active / managed 条件。不能让历史版本或链接资产参与错误匹配。

准备阶段的查重结果可带上版本或变更序列，在没有相关变化时复用；发生变化才重新分类。缺失指纹的历史文件应按需、渐进回填，避免每次导入都重新读取；不能先同步扫完整个库再允许导入。

### 序列识别有重复目录工作与数组复制

`probeImageSequenceImportOffer`（`:13139` 附近）及 `expandImageSequenceSourcePaths`（`:13107`）按每个选中文件重新枚举父目录，并调用 `findImageSequenceContaining`。后者每次重新运行完整 `detectImageSequences`（`src/shared/image-sequence.ts:263`）。探测中的尺寸缓存避免了一部分重复媒体读取，但没有避免重复列目录、分组、排序及遍历同一序列。

此外，`detectImageSequences` 在连续帧分支使用 `run = [...run, frame]`（`:246`），长度为 L 的连续序列会累计复制平方级数量的数组元素。

候选：每个源目录只列举、分组和排序一次，建立帧路径到候选序列的反向映射；连续段就地追加，结束后保存该段并换一个新数组，避免改变结果数组。按目录批处理与数组追加是两项独立优化，应分别验证，不能把整个预探测路径的收益归给一行改动。

重复源目录枚举只影响实际进入序列探测/展开的路径，不应泛化为所有导入。普通文件、整个文件夹、拖放、确认序列及自动化入口需要分别列清楚。连续帧数组复制则还影响普通导入内部两次建立 `sequenceBatchPaths` 的检测；它们用于避免误判序列中的重复帧，即使关闭序列分组也不能直接删去。

渲染端 `src/renderer/post-import-image-sequences.ts:71` 和 `:98` 附近还有逐帧 `candidate.frames.find` 的平方级映射，可复用 Worker 既有按路径建立 Map 的做法。此次仅确认源码结构，未对这部分做性能测量。

### 复制后再次完整读取 stage

`copySourceSnapshot`（`:13020` 附近）已经逐块读到源字节，但丢弃了可用于计算哈希的缓冲区；`stageOneImportSourceEntry`（`:48690`）随后重新打开并读取 stage 计算两个哈希。

可评估把两个哈希更新并入复制循环，减少一次完整 stage 读取。现有 SHA-256 和 SHA-1 已经在同一次 stage 遍历中计算，不能把“合并两种哈希的读取”当成尚未实现的收益。融合复制与哈希还须明确哈希代表的字节、部分写入、源变化、刷新失败及 stage 校验语义，不能仅删掉检查来取得更快数字。

复制和哈希 helper 各按文件申请 1 MiB 缓冲区，400 个小文件对应约 800 MiB 的累计缓冲区容量申请，不等于实际读取量或 RSS 峰值。按任务租用、复用有界缓冲区或按文件大小限制申请，是另一个可单独测量的候选。

### 普通导入的事务粒度与事务内文件操作

普通路径逐资产提交（`:45224` 附近）；事务内还做图片头部读取、元数据 JSON 写入，以及搜索索引同步（`:45322–45383`）。图片头探测本身已有读取上限，不是完整图片解码。

候选为先在事务外准备需要的数据，再按有界子批提交，子批成功后统一发布这一批的变化并让出 Worker。提交粒度须结合首屏、取消和故障恢复测量决定，不能直接用一个覆盖整个导入的超长事务。

已有 bulk 路径的外层事务不能直接套在普通导入上：现有循环会在内层事务返回后更新 `affectedAssetIds`、发送事件；外层事务尚未成功时，这些资产不能被当成已持久化。必须调整子批提交状态、通知及恢复边界。数据库仍保持现有持久性设置。

## 当前已经存在的能力

- stage 到 Assets 已经使用同库 `renameSync`。普通导入保留用户源文件，不能把源文件直接移走当成复制优化。
- 两种哈希已经共用一遍 stage 读取。
- handler 在导入期间已有 `withMediaSchedulingSuspended`，不能再次建议把“暂停缩略图调度”当作新改进。
- 已有预编译语句缓存、分块查询及有界图片头探测，应复用，而不是重新实现。

## 本地验证及排序

本轮按用户要求收敛到源码分析和最小隔离实验，未执行全链路逐阶段 profiling，也未执行更多媒体工作负载。仅存在代码依据的候选不标为已验证收益；实验原型不等于生产实现或故障恢复验收。

名称查询实验复用了与当前源码一致的相关列及 managed / linked 部分索引，构建内存 SQLite 夹具（20,000 条资产，其中 18,000 托管、2,000 链接），比较 400 个不存在的名称。查询计划确认：原条件为 `SCAN assets`，添加托管条件后为 `SEARCH assets USING INDEX assets_managed_path_identity_unique (path_identity=?)`。8 项断言通过。

| 查询策略（单轮隔离测量） | 耗时 |
| --- | ---: |
| 原条件，语句预编译后查询 400 次 | 193.770 ms |
| 补托管条件，复用现有索引查询 400 次 | 0.141 ms |
| 查询全库并建 20,000 条 Map | 14.294 ms |
| 已建 Map 的 400 次查询 | 0.052 ms |
| 建 Map 加上查询 | 14.346 ms |

这说明“数据库已有字段却仍重复扫描”的问题确实存在，也支持优先考虑范围正确的索引点查 / 本批预取。它不是完整资源库 schema 或磁盘数据库，不包括孤儿文件检查、复制、哈希、提交或 IPC；没有预热与多轮统计，不能把比例当成端到端导入加速倍数。完整 SQL、DDL、计划和数值见[原始记录](2026-10-19-import-lookup-indexes-results.json)。内容哈希查询本轮没有测量。

建议实施顺序：

| 优先级 | 增量 | 依据 | 需要的生产验证 |
| --- | --- | --- | --- |
| 第一批 | 统一托管目标点查 / 本批分块预取、复用语句、按阶段复用磁盘目录映射 | 字段和部分索引已有；重复遍历目的地已有 PR70 A/B 证据 | 普通/链接隔离、缺失文件、Unicode 孤儿、目录/符号链接、外部写入、keep-both；复跑大库/小批 A/B |
| 第一批 | 当前版本的大小+内容指纹查询索引及连接方式；缺失值渐进回填 | 当前查重路径反复执行，源码未见相应内容索引；收益尚未做端到端验证 | 同内容异名、历史 revision 排除、替换后哈希失效、NULL 指纹、当前版本变更；同大小素材库 A/B |
| 第二批 | 序列按目录检测一次、去掉连续段反复复制及逐帧 find | 轻量原型输出等价且算法耗时下降 | 复用现有序列单测，补入口开关、补帧、断号、padding、尺寸不一致、重复帧的真实导入测试 |
| 第三批 | 复制与两个哈希共用一次字节遍历、缓冲区复用 | 现有复制循环之后存在一次完整 stage 读取；收益尚未测量 | 源变化、短读/部分写入、取消、刷新失败、空文件、超大文件、数据一致性 |
| 第四批 | 有界子批提交、事务外准备元数据、提交后合并事件 | 普通路径每资产提交，涉及恢复语义，尚无本轮隔离收益数据 | 进程中断后重启对账、子批中途失败、部分成功、取消、真实 UI 渐进刷新和首屏延迟 |

先消除库规模乘以导入数量的重复工作，再评价剩余提交和 I/O 成本。暂不基于猜测给并发度或子批大小固定数值，也不改变 COPY 保留源文件或现有持久性设置。
