## 算法判断

旧路径对每个待导入资产重复调用 `portableDiskDestination`，逐段枚举目录并比较 portable identity。假设已有文件数为 N，待导入数为 M，扁平目录下目录项处理成本约为 O(MN)，而不是在所有场景下都严格 O(M²)。当库规模和导入规模同步增长时会表现为平方级增长。

新路径在每次导入开始时查询资产表，构建目的地 Map；命中后直接返回，未命中则用 identity 拼接磁盘路径调用 `lstat`，仅在探测成功或非缺失错误时回到旧枚举路径。常见的无冲突扁平导入可把这部分工作降为约 O(N + M)，但要付出一次全库查询、Map 分配及每次未命中的元数据读取成本。全流程还包括复制、内容检测、事务、事件和媒体任务登记，不能把目录探测的加速倍数直接当作导入加速倍数。

## 实验边界

当前可测平台为 Windows x64、NTFS、NVMe。测试使用隔离的合成资源库和自有文件，测量真实 `LibraryService.prepareImport` / `resolveImport` 调用；文件体积及媒体构成不是正式 20,000 资产性能基线。结果仅用于隔离本 PR 的目的地查找收益，不代表真实大型图片、缩略图吞吐、机械硬盘、macOS 或整个应用的端到端表现。

每个场景校验 SQL 资产数与实际目录项数，测量前恢复已关闭资源库的同一数据库快照并删除本轮导入文件。两版本分别预热，正式样本交替 AB / BA 串行执行，且断言所有输入均成功导入、没有跳过。目录枚举统计同时记录调用数和返回目录项数。RSS 仅是同一个进程中的阶段采样，受两个模块共存、JIT 和 GC 影响，不能作为两版独立进程的峰值内存比较。

后续实施基准核对发现：本报告旧脚本逐轮恢复 DB、目标文件及操作目录，但没有逐轮移除生成的图片尺寸 artifact JSON；它们不参与 Assets 目录枚举，却意味着整个磁盘状态没有完全复位。消除重复目录枚举的机制证据仍成立，严格复位全部自有测试状态后的性能结论以后续导入加速实施基准为准。

作者在 PR 中的单轮 6,000 已有资产 / 400 导入数据只能作为实验线索。本报告的结论以本次重复测量及可复现语义测试为准。操作系统缓存未强制清空，不能声称冷盘性能。

首次 smoke 使用 Vite SSR module loader，在初始化下游模块时触发 transport timeout，尚未开始建库或导入；该次没有有效样本。随后改用 Vite 构建 CJS、将外部依赖保留给 Electron Node runtime 加载的方式。初始化、构建、建库和关闭清理不计入导入耗时。

## 结果与建议

**方向合理，大批量收益明确；当前候选因两项 P1 行为回归不建议直接合并。**

原始样本：[完整 JSON](2026-10-19-pr70-import-performance-results.json)。运行环境：Electron 43.1.0，内置 Node 24.18.0，原生模块 ABI 148，Windows x64 / NTFS / NVMe。以下均排除预热样本。

| 场景 | 配对轮数 | 基线总耗时中位数（范围） | 候选总耗时中位数（范围） | 配对耗时降幅中位数（范围） |
| --- | ---: | ---: | ---: | ---: |
| 20,000 已有文件 + 400 导入 | 5 | 19.232 s（17.614–19.737） | 6.090 s（5.680–6.701） | 68.06%（66.05–69.75%） |
| 20,000 已有文件 + 1 导入 | 3 | 539.825 ms（519.065–565.599） | 486.744 ms（451.846–671.187） | 6.23%（−24.33–20.11%） |

大批量场景按两个总耗时中位数相除约为 **3.16 倍吞吐**；配对节省时间中位数为 **13.142 秒**。准备阶段中位数为 **13.170 → 3.076 秒**，应用阶段为 **5.978 → 2.897 秒**。阶段中位数分别计算，不能简单相加代替总耗时中位数。

每轮 400 文件导入，基线在准备阶段枚举目录 1,200 次、处理 24,000,000 条目录项，应用阶段 400 次、8,000,000 条，合计 **1,600 次 / 32,000,000 条**；候选均为 **0**。目的地探测接缝统计的 `lstat` 调用数两版均为准备 1,200 次、应用 400 次，说明收益主要来自消除反复枚举，而不是消除所有磁盘元数据访问。这些计数仅涵盖目标 Assets 子树的枚举及目的地探测接缝，不是全进程所有 I/O。

单文件场景的总耗时波动较大，3 对不足以认定稳定加速或稳定退化。准备阶段候选三次均较慢，配对多花 **0.585–16.578 ms**，中位数 **16.117 ms**；这是每次全库建索引固定成本的信号，但本次没有进一步单独计时 SQL 与 Map 分配，不能将准备阶段差值全部归因于某一步。

5 对大批量样本全部改善，机制计数与耗时变化方向一致，足以支持“本次工作负载下优化有效”。没有通过单轮结果推断普遍加速，也没有用 3 或 5 个样本估计 P95、声称统计显著，或把 warm-cache NVMe 数据当作机械硬盘证据。剩余耗时可能由复制、日志、事务及其他处理共同构成；本次没有隔离 `fsync`，不把余量全部归因于事务提交。

## Spec：已确认的行为回归

独立证据见[完整正确性审查](2026-10-19-pr70-import-correctness.md)。该审查用两个固定版本分别执行真实 Worker 准备导入流程，Windows 上三组断言通过：

| 需求条目 | 实现位置（候选提交） | 自动化证据 | 平台 / 人工证据 |
| --- | --- | --- | --- |
| 保留磁盘孤儿文件的 portable 名称冲突 | `DiskFallbackDestinationIndex.get`，`library-service.ts:4198` | `scripts/repro-pr70-import-conflicts.mjs`：NFD/NFC、Unicode 折叠两组，基线均报 1 个冲突，候选均报 0 个 | Windows Worker 已执行；未执行 UI 人工验收或导入应用 |
| 托管目标仅与托管目的地比较 | `destinationIndexWithDiskFallback`，`library-service.ts:13069` 及所调用的查询 | 同一复现脚本：仅链接根有同名文件时，基线报 0 个冲突，候选报 1 个 | Windows Worker 已执行；未执行 UI 人工验收或决策后的应用 |

两项均由独立审查列为 P1。第一项说明 portable identity 只能用作比较键，不能假定它就是磁盘可解析路径；第二项说明直接复用已有 helper 也需检查其查询范围。

建议保留减少重复枚举的方向，但合并前修复这两项：托管目的地查询显式限定 `location_kind = 'managed'`；磁盘查找可以按目录惰性建立一次实际名称到 portable identity 的映射，并在批次内复用，避免把精确路径 `lstat` 未命中当作 portable 名称不存在。该方案仍须处理目录 / 符号链接 / 名称歧义、应用阶段状态变化和错误传播，再补回归及重新测量，不能直接把建议当作已验证的修复。
